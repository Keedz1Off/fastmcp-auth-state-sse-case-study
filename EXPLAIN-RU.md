# FastMCP: как объяснить кейс

## Рассказ на минуту

«Я исследовал авторизацию, жизненный цикл SSE-сессий и сохранение OAuth-состояния. В главном кейсе сервер правильно вернул 401 после отзыва тестового доступа, а инструмент не выполнился повторно. Но клиентский RPC продолжал ждать: транспорт записал ошибку, не передав её ожидающему вызову. Я сравнил поведение без RPC-deadline и с ним, затем проверил независимый клиент и event loop. Поэтому результат — дефект обработки ошибки, а не доказанный обход авторизации или DoS».

Произноси от своего лица только то, что можешь сам объяснить и защитить. Работа выполнялась с AI-assisted анализом и инструментами, не полностью вручную.

## Нормальный флоу

Host/агент выбирает tool → FastMCP Client → транспорт → MCP server → настроенная аутентификация и прикладные разрешения → tool → backend → ответ.

MCP — протокол связи. FastMCP — библиотека клиента и сервера. LLM в этой схеме может выбирать действие, но не заменяет серверную проверку прав.

В legacy SSE сервер держит отдельный поток событий к клиенту, а клиент отправляет сообщения через HTTP POST. Ошибка POST и состояние потока — не одно и то же.

## Главная проблема: почему клиент ждал

RPC — один запрос с ожидаемым ответом. Фоновый writer отправляет его серверу. Сервер отвечает 401, то есть правильно запрещает действие. Writer логирует ошибку, но ожидающий RPC не получает её напрямую. Поток чтения и session task остаются активными.

Без RPC-deadline вызов оставался pending на двухсекундной границе наблюдения; затем стенд отменял его. Это не доказательство бесконечного зависания. С deadline 0.5 с появился MCPError примерно через 0.52 с.

Независимый клиент и heartbeat event loop успевали выполниться, пока первый вызов ещё ждал. Значит, «один запрос завис» не равняется «всё приложение перестало работать».

## Остальные четыре наблюдения

**1. Параллельный refresh.** Два процесса читают одно хранилище, но у каждого свой OAuthContext и lock. Общая БД не делает lock общим. При ротации старого refresh token один первоначальный refresh был отклонён, после чего произошла повторная авторизация. Позднее процессы обновляли разные пары токенов — это не доказательство согласованного exactly-once refresh.

**2. Прерванная запись.** Новая пара токенов и абсолютный срок действия записывались отдельно. Контролируемый выход процесса между записями оставил новую пару со старым expiry. База SQLite оставалась целой. Явный повтор исправил состояние в тесте; автоматическое исправление не доказано.

**3. Отзыв public client.** В прежней проверенной комбинации SDK запрос отзыва без client_secret завершался invalid_request. Confidential client работал. Это совместимость конкретного flow, не доказанный обход авторизации. Отдельный SSE-кейс с реальным локальным запретом сервером — другая проверка.

**4. Windows ACL.** Унаследованные разрешения давали дополнительным смоделированным SID права на файлы cache вопреки выбранной owner-only политике. Реальный вход второго пользователя не запускался. Доступ к ключу и раскрытие plaintext-токена не показаны.

## Почему EpicStaff не превратил это в подтверждённую уязвимость

В коде найден реальный Redis-worker с поддерживаемым PrefectHQ Client → SSE путём. Но там другая комбинация версий и уже задан 30-секундный timeout ответа; отдельно 10 секунд на initialize handshake. По коду deadline доходит до ожидания ответа.

Это статический разбор, приложение не запускалось. 30 секунд не означают верхнюю границу всей задачи: отдельно есть соединение, несколько RPC, модель и cleanup. При штатной остановке worker дожидается in-flight задач. Отмена локального ожидания не гарантирует прекращение удалённого действия.

## Вопросы техлида

**Это auth bypass?** Нет: сервер вернул 401 и tool body не выполнился снова.

**Это DoS?** Не подтверждён. Есть pending RPC, но нет доказанного нарушения общей доступности.

**Зачем нужен здоровый контроль?** Чтобы проверить альтернативу «весь event loop или сервер уже не работает».

**Почему тесты passed, если баг есть?** Наблюдательный тест может правильно подтвердить ошибочное поведение. Passed не означает исправление продукта.

**Ты прогнал upstream полностью?** Был полный default selection на закреплённом snapshot, 9,856 items; результат остался красным: 19 unsuccessful. Не весь возможный набор окружений/opt-in тестов.

**Какая главная ценность работы?** Прослеживание серверного отказа до клиентского ожидания, проверка состояния на независимых источниках и отказ от преувеличения влияния.
